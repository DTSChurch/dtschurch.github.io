How the Sync Works

One Rock job — the Overflow Sync Job — drives everything. It uses the credentials and settings saved on the gateway, runs four independent stages, and reports a detailed summary every time. This page explains what each stage does, how records are matched, and how special gift types are handled, so you can read a run summary with confidence.

The Four Stages

Each stage can be toggled independently on the job (Setup Step C). They run in order, and each adds its own block to the run summary. If one stage hits a problem, the others still run; the job reports a warning at the end.

StageWhat it does
1. Sync People Pulls Overflow donor profiles, finds or creates the matching Rock Person, and records a durable link between the donor and that person.
2. Sync Subscriptions Pulls Overflow subscriptions (recurring gifts) into Rock scheduled transactions, including the saved payment method and giving detail.
3. Sync Transactions Pulls contributions from the rolling window into Rock financial transactions. One-time gifts stand alone; recurring gifts are linked to their scheduled transaction.
4. Perform Batching Groups the synced transactions into Rock batches by date / campus / payment method (per your gateway settings) and recalculates each batch’s control amount.

Window note: only the transactions stage uses Sync Days Back (30 by default). People and subscriptions always pull in full.

How People Are Matched

To avoid duplicates, the sync matches an Overflow donor to a Rock person in this order:

  1. By existing link. If the donor is already linked to a Rock person, that record is used.
  2. By identity. Otherwise it looks for a Rock person matching the donor’s first name, last name, and email.
  3. Create new. If there’s still no match, a new Rock person is created.

Either way, the donor and person are tied together by a Person Map (the durable Overflow-donor ↔ Rock-person link). Future runs reuse that map, so the same person is updated rather than re-created. If a Rock person is later merged with another, the link follows the surviving record automatically.

How Campaigns Are Matched

Each gift references an Overflow campaign (and optionally a subcampaign). The sync resolves the Rock account like this:

Mapped

A Campaign Map links the campaign / subcampaign to a Rock Financial Account — the gift posts there.

Unmapped → fallback

No map, but the gateway has a default Account — the gift posts to the fallback account.

Unmapped → auto-create

No map, and Create Accounts If Not Mapped is on — a Rock account and map are created automatically, then the gift posts there.

Unmapped → skipped

No map, no default, auto-create off — the gift is skipped and listed in the Skip Reason Breakdown.

Auto-created accounts are named from the campaign and subcampaign names (truncated to Rock’s 50-character limit), created flat (no parent, campus, or GL code), and the creation count appears as an Accounts Created line in the summary. The behavior is idempotent — later runs reuse the same map.

Special Gift Handling

Overflow specializes in non-cash giving, so a few gift types get special treatment:

TypeHow it’s handled
Stock Only synced once the gift reaches liquidation complete (the proceeds are final). Uses the gateway’s Stock Currency Type (Non-Cash by default).
Crypto Only synced once the gift is paid out. Uses the gateway’s Crypto Currency Type, or the underlying card/ACH method if that’s left blank.
Refunds & voids A refunded or voided gift creates an offsetting negative transaction with the same date and amount, linked to the original so Rock’s UI shows it as a refund. The two net to zero.
Chargebacks Handled the same way as a refund — an offsetting reversal linked to the original, carrying a “Chargeback on <date>” note.
Failed / pending Governed by the Failed Transaction Handling setting. By default these are not imported until they settle. See Troubleshooting for the four modes.

Reversals (refund / void / chargeback) always wash to zero regardless of the Failed Transaction Handling setting — that setting only governs failed and cancelled gifts.

Idempotency & Resilience

  • No duplicates. Each contribution is keyed by its Overflow ID (refunds use a -R suffix). Re-running the job updates the existing Rock transaction instead of creating a new one.
  • One bad record won’t poison the run. Records are saved individually, so a single failure is counted as a skip with a reason and the rest of the batch still processes.
  • Re-runs are safe. Because matching and keying are durable, you can run the job as often as you like — on the schedule or via Run Now — without risk of double-counting.

Reading the Run Summary

After every run, the job’s Result message reports, per stage:

  • Created / Updated / Skipped counts for the records it processed.
  • Accounts Created — how many Rock accounts were auto-created (when that setting is on).
  • Transactions Removed — used by Failed Transaction Handling mode 4.
  • Skip Reason Breakdown — grouped reasons with up to five human-readable examples each: campaign / subcampaign names (with the Overflow ID in brackets), the dollar amount, and the donor name. This is the fastest way to see what didn’t import and why.

If any stage caught an error, the job ends with a warning so it’s visible in the Jobs grid.

Running On Demand

You don’t have to wait for the schedule — click Run Now on the Overflow Sync Job at any time. Because the sync is idempotent, an on-demand run alongside the scheduled one is safe.

What the Sync Does Not Do

  • It doesn’t push gifts entered in Rock back to Overflow — the giving direction is Overflow → Rock.
  • It doesn’t import gifts outside the configured transactions window unless you widen Sync Days Back.
  • It doesn’t reconcile or close batches for you — batching only groups transactions and recalculates open-batch totals.
